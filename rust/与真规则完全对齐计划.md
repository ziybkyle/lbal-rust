# 与真规则完全对齐：实施计划与操作手册

版本：v0.1  
适用范围：`godot_kernel/rust`  
参考版本：Steam 版本号 `16940935`、BetterLandlord `1.2.7`、SlotWeave `1.0.0`、Godot `3.4.4`

## 0. 一句话目标

同一个种子文本、同一串操作，在真规则版和 Rust 版里必须得到同一副牌、同一个棋盘、同一组候选、同一串事件、同一笔收入、同一个胜负结果。

这里的“完全一致”不包括界面、动画、音乐、音效和纯装饰随机；这些可以不同，但必须证明它们不会改变游戏状态。

## 1. 先统一几个词

| 词 | 含义 |
|---|---|
| 真规则版 | 本地 `godot_kernel/game` 里的原版游戏脚本，加上 BetterLandlord 的随机数接管。它是可以自动跑、可以导出完整状态的“金标准”。 |
| Steam 版 | 你电脑上安装的 Steam 客户端，版本号 `16940935`，已装 BetterLandlord。它是最终要对的真实版本，但自动化成本高。 |
| 种子文本 | 玩家看到的字符串种子，例如 `B2AG00000000`。 |
| 房东种子 | 种子文本按 BetterLandlord 规则算出的 31 位整数，英文名 `landlord_seed`。 |
| 随机流 | 一组独立的随机数序列。真规则把不同用途拆成不同流，例如转轮、效果、奖励、小字。 |
| 轨迹 | 一局里每一步的完整状态、候选、选择、事件和收入，按顺序写成 JSON 行。 |
| 事件 | 一次具体的效果触发，例如“煤炭变成钻石”“猫吃掉相邻的牛奶”“物品给金币”。 |
| 场景 | 一个受控开局：指定牌组、棋盘、物品、精华、小字、租金和种子，然后跑固定几步。用来精确覆盖单个规则。 |

## 2. 目标等级

按从浅到深分五层，必须逐层通过：

| 等级 | 内容 | 验收标准 |
|---|---|---|
| L0 | 随机数一致 | 同种子文本得到同一个房东种子；各随机流前 100 个值一致；同样数组的洗牌结果一致。 |
| L1 | 开局一致 | 初始牌组顺序、初始转轮顺序、第一次三选一候选、第一次物品候选一致。 |
| L2 | 单旋一致 | 同一旋的棋盘、牌组、物品、精华、小字、收入明细、事件顺序完全一致。 |
| L3 | 整局一致 | 固定 1000 个种子的完整轨迹一致，包含房东战和胜负。 |
| L4 | 真机一致 | Steam 端固定种子、固定操作的轨迹与 Rust 一致；不能自动化的部分有单独说明。 |

最终交付必须达到 L0–L3 全部通过，L4 用可自动化的样本通过。任何一项不能通过，都必须写成明确的例外，不能默默近似。

## 3. 当前状态和主要差距

### 3.1 已经有的东西

- Rust 规则核心：`crates/lbal_core/src/state.rs`、`run.rs`、`rng.rs`。
- 批量命令行：`crates/lbal_cli/src/main.rs`，支持局数、种子、线程、重放、结果导出。
- Python 接口：`crates/lbal_py/src/lib.rs`，支持单环境和批量环境。
- 评估工具：`python/eval_policy.py`、`python/align_report.py`、`python/compare_runs.py`。
- 保真度记录：`FIDELITY.md`、`RUST_PORT_PLAN.md`。
- 真规则侧：`game/` 是打好补丁的原版工程；`patches/files/rng_infra.gd` 是 BetterLandlord 随机数的完整参考实现。

### 3.2 对齐前的数字（阶段 0 快照，已被后续实现推翻，仅保留作对照）

下表是 2026-11-04 开工时的状态。阶段 1–2 已经把随机数、棋盘模型、洗牌和候选生成全部重做，所以这些数字只用来衡量进步幅度，不能当作现在的结论。当前数字见第 22 节与 `FIDELITY.md`。

| 项目 | 结果 |

| 完整手工策略接 Rust（当时） | 600 局，胜率 27.8%，区间 24.4%–31.6% |

| 带物品的 6–12 旋（当时） | 115/200 = 57% |

注意：表里 600 局 27.8% 那一行与现在的复测差得很远（当前同批种子只有 10%~13%），说明当时的规则或适配器与现在不是同一套，直接引用会造成误导。

### 3.3 开工时的主要差距（阶段 0 快照，已基本解决）

| 差距 | 现状 | 影响 |
|---|---|---|
| 随机数 | Rust 只有一个 `Pcg32::seed_from_u64`；真规则是 11 条持久流、5 条每旋流、物品/精华序列流 | 同种子完全对不上；出牌顺序、候选、效果触发都不同 |
| 棋盘模型 | Rust 只有 5×4 的 20 格；真规则每个转轮有完整图标数组和屏幕外图标 | 牌组超过 20、生成物、箭头、行列效果会错位 |
| 洗牌算法 | Rust 用普通洗牌后按 `position % 5` 分列；真规则用 `shuffle_tiles()` 的两段洗牌和空格交换 | 棋盘顺序不同，后续所有随机都错位 |
| 奖励候选 | Rust 用池子随机抽；真规则用按稀有度的符号流、物品序列、精华序列、光标的组合 | 候选内容和顺序不同 |
| 物品状态 | Rust 只有物品列表；真规则有启用/禁用、计数、存档值、存活/销毁、最近销毁 | 物品效果、候选过滤、房东战都会偏 |
| 精华状态 | Rust 只有持有列表；真规则有充能、存档值、消耗、永久加成登记 | 后期成长引擎偏简单 |
| 小字 | 部分动态图标并列时 Rust 按名字排序；真规则用 `fineprint` 流随机抽取 | 同种子结果不同；依赖小字的规则会偏 |
| 房东战 | Rust 有血量、租金和胜负；真规则有完整小字生成、伤害和阶段行为 | 第 9–12 档租金差距明显 |
| 数据版本 | 目前靠人工确认 | Steam 更新后可能悄悄漂移 |

## 4. 总体方法

### 4.1 真规则是唯一的金标准

- 规则以 `game/` 里的原版 GDScript 为准，不以 Python 计算器为准。
- BetterLandlord 的 C# 源码可以作为随机数的第二参考，但以 `patches/files/rng_infra.gd` 在 Godot 里的实际行为为准。
- 对不确定的规则，先写一个受控场景，让真规则跑一次，再照结果实现 Rust，不靠猜。

### 4.2 先做比较器，再改规则

不要一边改 Rust 一边凭感觉判断。顺序是：

1. 定义轨迹格式。
2. 真规则导出轨迹。
3. Rust 导出同样格式。
4. 差异工具指出第一个不同点。
5. 只修这个不同点。
6. 加回归测试，再进入下一个。

### 4.3 用同一串操作，排除策略差异

规则对齐时，Rust 不自己决策，而是回放真规则里记录的选择。这样差异只可能来自规则或随机数，不会来自“策略选得不一样”。

### 4.4 一套规则，不维护两套

过渡期可以用编译开关控制轨迹导出，但不能长期保留“近似规则版”和“精确规则版”两套核心。精确版通过验收后，删除近似路径，避免训练和评估用到不同规则。

### 4.5 小步提交，每步有证据

每个提交必须包含：

- 一个失败的轨迹或场景；
- 对应的修复；
- 修复后通过的测试；
- 更新后的覆盖清单。

## 5. 阶段计划

### 阶段 0：冻结参考版本

**目标：** 确保后面所有对比都基于同一份游戏数据和同一套模组。

任务：

1. 记录 Steam 版本号、游戏包哈希、`game/JSON` 四个文件的哈希。
2. 记录 BetterLandlord、SlotWeave、LuckyAssociations、Rewind 的版本。
3. 确认 `godot_kernel/game` 只包含自动化补丁和随机数补丁，没有改动玩法脚本。
4. 生成 `alignment/manifest.json`，包含：
   - 游戏版本号；
   - 数据文件 SHA256；
   - 模组版本；
   - Godot 版本；
   - 生成时间。
5. 加一个启动检查：数据哈希或版本不一致时，轨迹对比直接报错。
6. 重新从当前 PCK 导出 JSON，确认符号、物品、精华、小字数量和仓库记录一致。

交付物：

- `alignment/manifest.json`；
- `python/check_alignment_versions.py`；
- 一份版本记录说明。

验收：

- 同一份版本清单下，真规则和 Rust 读到的数据完全一致。
- 改动数据或模组后，检查脚本能明确报错。

### 阶段 1：建立轨迹对比器

**目标：** 能看清“第一个不同点”在哪里，而不是只比较最终收入。

任务：

1. 定义 `lbal-trace-v1` 格式（见第 8 节）。
2. 真规则导出：
   - 新增 `RL_TRACE` 模式；
   - 每局一个 JSONL；
   - 包含开局、每旋状态、事件、候选、选择、收入明细。
3. Rust 导出：
   - 命令行新增 `--trace-json`；
   - Python 接口新增完整状态读取；
   - 输出同一格式。
4. 写 `python/trace_diff.py`：
   - 先比头部：种子、房东种子、版本、初始牌组；
   - 再比每旋状态：牌组、转轮、棋盘、物品、精华、小字、代币；
   - 再比事件：缺失、多余、顺序、数值；
   - 最后比候选和选择；
   - 输出第一个差异的字段路径和上下文。
5. 建立三组种子：
   - 冒烟组：5 个种子，前 3 旋；
   - 回归组：200 个种子，前 12 旋；
   - 全量组：1000 个种子，整局。
6. 先让“无效果、无物品、前 3 旋”的轨迹一致，证明对比器本身可靠。

交付物：

- 轨迹格式文档；
- 真规则导出器；
- Rust 导出器；
- 差异工具；
- 三组种子清单。

验收：

- 对比器能准确指出“第几旋、哪个字段、真规则是什么、Rust 是什么”。
- 在一个人为制造的差异上，工具能报出预期位置。

### 阶段 2：重做棋盘模型和随机数

**目标：** 同种子文本得到同一个初始牌组、同一个转轮顺序、同一组候选。

这个阶段是核心重构，不是补几个函数。

任务：

1. 实现 BetterLandlord 随机数类（见第 5 节）。
2. 实现随机流容器：持久流、每旋流、物品/精华序列、光标和计数器。
3. 增加种子文本接口：
   - 命令行 `--seed-text`；
   - Python `Env(seed_text=...)`；
   - 轨迹头部记录种子文本和房东种子。
4. 重做牌组和转轮状态：
   - 每个符号有稳定编号；
   - 每个转轮有完整图标数组；
   - 保留屏幕外图标；
   - 保留可见窗口和行列位置；
   - 保留 `icon_types_to_be_added` 的添加顺序。
5. 按真规则实现 `shuffle_tiles()`：
   - 收集所有图标和空格；
   - 超过 25 个时移除多余空格；
   - 用 `reel_shuffle` 洗牌；
   - 按 `(i - passes) % 5` 分到转轮；
   - 对可见空格再洗一次并交换屏幕外非空格；
   - 更新 `icon_types` 和位置。
6. 按真规则实现奖励候选：
   - 符号稀有度用 `sym_rarity`；
   - 各稀有度池用 `sym_common` 等流；
   - 强制稀有度数组用 `forced_rarity` 洗牌；
   - 物品用 `itemseq_...` 序列和光标；
   - 精华用 `essenceseq_...` 序列和光标；
   - 物品稀有度用 `itmrarity_...` 派生；
   - 池子先按名字排序，再洗牌；
   - 过滤已持有和最近销毁的物品；
   - 序列用完时用 `itemfb_` / `essfb_` 派生兜底。
7. 按真规则实现小字选择：
   - 用 `fineprint` 流；
   - 动态图标并列时用 `fineprint` 流随机，不按名字排序；
   - 保留 `dynamic_icon`、依赖类型/分组、难度过滤。
8. 审计所有随机调用点：
   - 禁止游戏规则使用单一全局流；
   - 非玩法随机只能用 `cosmetic` 或 `scratch`；
   - 检查没有残留的原生 `randomize()`、`randi()`、`rand_range()`。

交付物：

- 新的随机数模块；
- 新的转轮/棋盘模型；
- 新的候选生成器；
- 随机数对照夹具；
- 开局一致性测试。

验收：

- 20 个种子文本，前 100 个随机值逐值一致。
- 20 个数组洗牌结果一致。
- 20 个种子，初始牌组、初始转轮、第一次符号候选、第一次物品候选完全一致。
- 5 个种子，前 3 旋无效果轨迹完全一致。

### 阶段 3：对齐旋转和效果管线

**目标：** 同一旋的事件顺序、数值、目标、销毁、生成、加算、乘算完全一致。

任务：

1. 把旋转流程拆成与真规则相同的阶段，并固定顺序：
   - 旋前变换和物品钩子；
   - 基础值；
   - 加算阶段；
   - 乘算阶段；
   - 物品加算；
   - 物品乘算；
   - 旋转后效果；
   - 销毁和生成；
   - 收入、金币、租金、代币。
2. 对齐遍历顺序：
   - 按转轮、按可见行、按稳定编号；
   - 被销毁的符号不再结算；
   - 同一符号只结算一次；
   - 相邻、同行、角落、花色、分组都按真规则的坐标。
3. 对齐数值规则：
   - `values[0]` 是效果参数，不覆盖基础值；
   - 乘算只在结果非负时应用；
   - 永久加成、临时加成、成长计时分开；
   - 四舍五入/截断规则一致。
4. 逐个效果对齐：
   - 先按真实对局出现频率排序；
   - 再按获胜卡组出现频率排序；
   - 每个效果至少一个受控场景；
   - 记录触发条件、目标、数值、副作用、事件顺序。
5. 物品状态和开关：
   - 增加启用/禁用；
   - 增加计数、存档值、使用次数、销毁状态；
   - 增加“获得时立即结算”和“手动使用”的区分；
   - 增加 `recently_destroyed_items`，用于候选过滤。
6. 精华状态：
   - 充能、消耗、存档值；
   - 永久加成登记；
   - 同旋触发和跨旋触发；
   - 精华候选的序列、光标、兜底。
7. 小字：
   - 31 条全部实现；
   - 依赖符号/物品/分组时的动态图标；
   - 不可删、费用、收入修正；
   - 房东战每 150 伤害生成 3 条；
   - 生成顺序、队列和已存在过滤。
8. 房东战：
   - 血量、租金循环、伤害、胜负；
   - 小字生成；
   - 阶段行为逐一对照；
   - 第 9–12 档租金的差距单独统计。
9. 数据加载：
   - 字段缺失、类型错误、未知名字直接报错；
   - 数量断言；
   - 排序和索引稳定。

交付物：

- 事件级轨迹一致；
- 效果覆盖清单；
- 每个效果的场景和回归测试；
- 物品/精华/小字状态机。

验收：

- 200 个种子，前 12 旋轨迹一致率 100%。
- 固定 1000 个种子，整局轨迹一致率 100%，或只剩明确列出的非玩法例外。
- 所有符号、物品、精华、小字在清单里都有状态，没有“未验证”。

## 6. 随机数移植细则

### 6.1 种子文本到房东种子

真规则实现位置：`../patches/files/rng_infra.gd:62-73`。

步骤：

1. 输入文本先把 `O` 替换成 `0`，把 `I` 替换成 `1`。
2. 空文本或随机模式时，用 34 字符表生成 10 位随机种子；字符表不含 `O` 和 `I`。
3. 用 FNV-1a 计算 `landlord_seed`：
   - 初始值 `2166136261`；
   - 每个字符先异或，再乘 `16777619`；
   - 每一步都掩到 63 位；
   - 最后掩到 31 位。
4. 用 `derive_seed(base, name)` 派生各流：
   - 初始值 `base & 0x7FFFFFFFFFFFFFFF`；
   - 每个字符执行 `((h << 5) + h) ^ ord(c)`；
   - 每一步掩到 63 位；
   - 最后掩到 31 位。

注意：GDScript 的整数是有符号 64 位，移位和溢出行为和 Rust 不完全一样。实现时先用真规则生成一组对照值，不要只按理论写。

### 6.2 随机数类

参考实现：`../patches/files/rng_infra.gd:14-60`。

必须实现：

- 64 位状态和 64 位增量；
- 初始化：先步进，再加固定常数，再步进两次；
- `randf()` 返回 32 位结果除以 2^32；
- `randi_max(n)` 返回 `floor(randf() * n)`；
- `rand_range(min, max)`；
- `pick(array)`；
- `custom_shuffle(array)`：从末尾到 1，每次取 `floor(randf() * (i + 1))` 交换；
- `chance(percent)`：`randf() * 100 < percent`。

### 6.3 随机流表

| 流 | 创建方式 | 重置时机 | 用途 |
|---|---|---|---|
| `sym_rarity` | `derive(landlord_seed, "sym_rarity")` | 新局 | 符号候选稀有度 |
| `sym_common` | `derive(..., "sym_common")` | 新局 | 普通符号池抽取 |
| `sym_uncommon` | `derive(..., "sym_uncommon")` | 新局 | 非凡符号池抽取 |
| `sym_rare` | `derive(..., "sym_rare")` | 新局 | 稀有符号池抽取 |
| `sym_vrare` | `derive(..., "sym_vrare")` | 新局 | 极稀有符号池抽取 |
| `fineprint` | `derive(..., "fineprint")` | 新局 | 小字选择、动态图标并列 |
| `cosmetic` | `derive(..., "cosmetic")` | 新局 | 界面、音乐、装饰 |
| `forced_rarity` | `derive(..., "forced_rarity")` | 新局 | 强制稀有度数组洗牌 |
| `reel_init` | `derive(..., "reel_init")` | 新局 | 首旋前的转轮流 |
| `effect_init` | `derive(..., "effect_init")` | 新局 | 首旋前的效果流 |
| `scratch` | `derive(..., "scratch")` | 新局 | 音效、抖动等非玩法随机 |
| `reel` | `derive(spin_seed, "reel")` | 每旋 | 转轮放置、随机符号 |
| `effect` | `derive(spin_seed, "effect")` | 每旋 | 符号/物品效果 |
| `reel_shuffle` | `derive(spin_seed, "reel_shuffle")` | 每旋 | 棋盘洗牌 |
| `effect_shuffle` | `derive(spin_seed, "effect_shuffle")` | 每旋 | 效果中的数组洗牌 |
| `oil_can` | `derive(spin_seed, "oil_can")` | 每旋 | 油罐重掷列 |
| 物品序列 | `derive(landlord_seed, "itemseq_<rarity>_<round>_<event>")` | 每次物品候选事件 | 物品候选顺序 |
| 精华序列 | `derive(landlord_seed, "essenceseq_<round>_<event>")` | 每次精华候选事件 | 精华候选顺序 |
| 物品稀有度 | `derive(landlord_seed, "itmrarity_<round>_<counter>")` | 每次物品稀有度判定 | 物品稀有度 |
| 物品兜底 | `derive(landlord_seed, "itemfb_<rarity>_<event>_<cursor>")` | 序列用完 | 物品兜底 |
| 精华兜底 | `derive(landlord_seed, "essfb_<event>_<cursor>")` | 序列用完 | 精华兜底 |
| 每旋种子 | `derive(landlord_seed, "spin_<n>")` | 每旋 | 派生上面的每旋流 |

关键细节：

- 每旋的 `n` 是 `当前旋数 + 1`，在 `add_tba_symbols` 之前计算。
- `reel_init` 和 `effect_init` 只在首旋前使用，第一次 `begin_spin_rng` 后会被每旋流替代。
- 物品候选事件计数器 `item_pick_event` 每次物品候选加一，不按旋重置。
- 物品稀有度计数器 `item_rarity_ctr` 在新局重置，之后每次判定加一，不按候选事件重置。
- 物品/精华序列的池子先按名字排序，再洗牌。
- 候选过滤要排除已持有和最近销毁的物品。
- 序列游标在同一候选事件内连续使用，跨事件重新建序列。
- 真规则还会执行 `seed(landlord_seed)` 作为 Godot 全局随机种子。Rust 必须审计所有原生 `randi()`、`range()` 等调用；如果还有玩法调用，要纳入同一套对照，不能忽略。

### 6.4 棋盘洗牌

真规则实现位置：`../game/Main.tscn:4111-4174`。

必须按顺序实现：

1. 收集 5 个转轮里的全部图标，包括空格。
2. 记录空格列表和空格总数。
3. 当图标总数超过 25、还有空格、且允许漂亮空格时，从空格列表中移除一个空格。
4. 用 `reel_shuffle` 洗整个图标池。
5. 按 `(i - passes) % 5` 分到 5 个转轮；超过 25 后的空格跳过并计入 `passes`。
6. 重新计算每个图标的屏幕位置和 `grid_position`。
7. 收集屏幕外的非空格和可见空格。
8. 用 `reel_shuffle` 洗可见空格。
9. 把可见空格和屏幕外非空格成对交换。
10. 更新 `icon_types` 和 `saved_icon_data`。

当前 Rust 的 `Board::deal` 是“整副牌洗一次，然后按 `% 5` 分列”，和真规则不同。这个必须替换，不是调整参数。

### 6.5 候选生成

真规则实现位置：`../game/Pop-up.tscn:3883-4042`。

必须按顺序实现：

1. 判断当前是符号候选、物品候选还是精华候选。
2. 物品候选的稀有度用 `itmrarity_...` 派生；符号候选用 `sym_rarity`。
3. 强制稀有度数组用 `forced_rarity` 洗牌；精华强制项跳过。
4. 符号池按稀有度用 `sym_common`、`sym_uncommon`、`sym_rare`、`sym_vrare` 抽取。
5. 物品池：
   - 过滤已持有和最近销毁；
   - 用当前稀有度的物品序列；
   - 游标从上次位置继续；
   - 序列用完用 `itemfb_` 派生兜底。
6. 精华池：
   - 过滤已持有和最近销毁；
   - 用精华序列；
   - 游标继续；
   - 用完用 `essfb_` 派生兜底。
7. 候选数量、稀有度组合、保底和强制条件按租金档位读取真规则。

### 6.6 小字选择

真规则实现位置：`../game/Landlord.tscn:169-378`。

必须实现：

- 每 150 点收入伤害生成 3 条；
- 从 31 条候选里排除已存在和队列中的；
- 依赖符号/物品/分组的条件过滤；
- 动态图标候选并列时用 `fineprint` 流随机；
- 生成队列和实际生效顺序；
- 第 20 条金币不可删、第 21 条鸡蛋不可删、第 36 条虚空不可删等规则。

## 7. 规则对齐细则

### 7.1 状态模型

真规则的状态至少包括：

- 牌组：稳定编号、类型、基础值、永久加成、永久倍率、临时加成、临时倍率、显示次数、成长计时、存档值、来源。
- 转轮：每个转轮完整图标数组、可见窗口、行列位置、屏幕外图标、待添加图标。
- 物品：稳定编号、类型、启用状态、数量、存档值、使用次数、销毁状态、最近销毁列表。
- 精华：稳定编号、类型、充能、存档值、消耗状态、永久加成登记。
- 小字：编号、动态图标、依赖类型/分组、生效顺序。
- 经济：金币、租金、已交租次数、剩余旋数、重掷/删除/精华代币、房东血量。
- 流程：当前阶段、待处理候选、待结算精华、待添加符号、强制稀有度、强制跳过/强制选择。

Rust 当前缺少的部分，按上面的清单逐项补齐。

### 7.2 旋转流程

按真规则的顺序：

1. 检查能否旋转。
2. 设定每旋随机流。
3. 把待添加符号加入转轮。
4. 棋盘洗牌。
5. 计算旋前效果。
6. 计算基础收入。
7. 加算效果。
8. 乘算效果。
9. 物品加算。
10. 物品乘算。
11. 旋转后效果。
12. 销毁、生成、复活。
13. 结算收入、金币、租金、代币。
14. 生成候选和后续事件。

每个阶段的遍历顺序、目标选择和数值修改都必须和真规则一致。

- 一个不触发场景；

## 8. 轨迹格式

### 8.1 头部

```json
{"type":"header","schema":"lbal-trace-v1","seed_text":"B2AG00000000","landlord_seed":123456789,"build":"16940935","data_sha256":"...","mods":["BetterLandlord 1.2.7"],"floor":20,"initial_deck":[...],"initial_items":[...],"initial_essences":[...],"initial_fine_prints":[]}
```

### 8.2 每旋状态

```json
{"type":"spin","spin":1,"rent_due":25,"rents_paid":0,"coins_before":1,"coins_after":5,"spins_left":4,"tokens":{"reroll":0,"removal":0,"essence":0},"reels":[{"reel":0,"icons":[{"uid":1,"type":"coin"},{"uid":2,"type":"dud"}],"visible":[1,2]}],"board":[{"slot":0,"uid":1}],"items":[...],"essences":[...],"fine_prints":[{"num":20,"icon":"coin"}],"offers":[...],"events":[...],"income":{"total":5,"by_symbol":[{"uid":1,"value":1}],"by_item":[]}}
```

### 8.3 事件

```json
{"seq":1,"phase":"pre_spin","source_uid":1,"source_type":"coal","effect":"transform","target_uids":[1],"value_before":0,"value_after":5,"rng_stream":"effect","rng_index":3}
```

要求：

- `seq` 全局递增；
- `phase` 用固定枚举；
- `source_uid` 和 `target_uids` 用稳定编号；
- `value_before` / `value_after` 记录数值变化；
- `rng_stream` 和 `rng_index` 记录消耗；
- 同一事件的多个目标拆成多条，或明确 `target_uids` 顺序。

### 8.4 选择

```json
{"type":"decision","phase":"symbol_reward","offers":[{"uid":10,"type":"bee"}],"chosen_uid":10,"chosen_index":1,"skipped_uids":[11,12],"rerolled":false,"removal_uid":null}
```

### 8.5 对比规则

- 头部必须完全一致。
- 牌组、转轮、棋盘顺序和编号必须一致。
- 物品、精华、小字顺序和状态必须一致。
- 事件按 `seq` 逐条比较；缺失、多余、顺序不同都算差异。
- 候选内容和顺序必须一致。
- 选择按编号回放；如果编号对不上，先报编号差异，不继续比较后续。
- `cosmetic` 和 `scratch` 事件可以忽略，但必须有测试证明它们不修改游戏状态。

## 12. 风险和控制

| 风险 | 控制 |
|---|---|
| 随机数细节偏差 | 先写真规则对照夹具，再实现；逐值比较。 |
| 转轮模型重构大 | 单独阶段，先做无效果轨迹，再做效果。 |
| 效果顺序错 | 事件级轨迹；先修第一个差异。 |
| 物品状态复杂 | 状态机和场景测试；每个物品至少三个场景。 |
| 数据版本变化 | 版本清单和哈希检查；更新后重跑全量。 |
| 性能下降 | 正确性优先，阶段结束做性能门禁；不把轨迹日志放进普通模式。 |
| 两套规则漂移 | 只保留一套精确核心；过渡期用编译开关，验收后删除近似路径。 |
| Steam 模组干扰 | 用干净配置跑金标准；Steam 对照单独记录模组版本。 |
| 长尾效果拖慢进度 | 按真实出现频率和获胜卡组频率排序；但最终必须全部覆盖。 |

- 牌组名单是否一致（多了/少了哪些符号）。

## 22. 阶段 3 进度记录（2026-11-05，第六轮 / 本轮收尾）

### 22.1 本轮完成

**修正：reroll 物品的注册期随机数**

真规则的每旋注册顺序（`Main.tscn::_rl_add_effects`）：

1. `make_clumps()`
2. 每个物品 `add_conditional_effects()`（按持有顺序）
3. 含 `raritymod` 的图标 / dove 单独注册一遍
4. 所有图标 `times_displayed += 1`
5. 所有图标按 x 优先（列内 y）再注册一遍
6. `Items.add_cond_effects()`

`reroll` 物品在步骤 2 就会**急切求值**两个替换点数：
`floor(_itr_rand_range(1, 4))`（d3）与 `floor(_itr_rand_range(1, 6))`（d5），
每件 reroll 消耗 2 次 effect 流。真规则随后在条件评估时直接使用
这两个注册期点数，而不是再抽一次。

Rust 原来是在符号效果阶段（`d3`/`d5` 分支）才抽第二次，
导致整条 effect 流错位。已改为：

- `register_item_effects_pre_spin()`：在 `preregister_symbol_effects`
  之前按持有顺序为每件 reroll 抽 d3/d5 两个替换值；
- `d3`/`d5` 分支在 roll 小于阈值时复用该替换值，不再额外抽取。

验证（seed42 game_00004 / 真种子 `B2AG00000003`，spin 11）：

| 项 | 真规则 | Rust 修复前 | Rust 修复后 |
| --- | --- | --- | --- |
| effect 流前两次 | 0.7695 / 0.3644（reroll 替换值） | 当作 d5/d3 掷点 | 当作 reroll 替换值 |
| d5 | 4 | 4 | 4 |
| d3 | 1 → reroll 后 3 | 2（未触发 reroll） | 1 → 3 |
| 本旋收入 | 19 | 18 | 19 |

该局的首差异随之消失。

**诊断结论：检查阶段的重复注册会额外消耗 RNG**

真规则在 `_rl_check_effects` 中，每当一轮 `tbd` 符号被销毁：

- 对每个被销毁图标执行 `add_c_effs(true)`：先注册自身，再按
  `get_adjacent_icons()` 顺序注册 8 个邻居；
- 随后对全部 20 个图标再注册一遍（4821-4824 行）。

每次 `add_conditional_effects()` 都会重新求值注册期的随机参数
（d3/d5 掷点、seed/beehive/goose 等），因此**同一个 d3 一旋可能掷 1～5 次**。
但后续注册产生的效果会因 `get_cleaned_effect` 把
`anim == rand_texture_cycle` 的 `diff` 擦除而命中同一 hash，被去重；
所以**只有第一次注册的数值参与收入**，后续注册只推进 RNG 流。

用 `add_effects`/`itemreg`/`sce`/`d3reg` 临时标签在 seed42 前 7 局确认了
上述顺序（标签已还原，不留在游戏脚本中）。seed42 的 `rng_tags` 统计：

- 483 个旋有标签；其中 252 旋只含 dice 标签；
- 盘面 1 个骰子对应 1～5 次 dice 抽取（159 旋 1 次，24 旋 2 次，16 旋 3 次，
  4 旋 4 次，1 旋 5 次）；
- reroll 存在的旋序列为 `item,item,dice,dice,item,item,item,item`
  （两次注册期替换值 → 骰子 → 销毁后的两次物品重注册）。

这条“销毁后重注册”尚未在 Rust 建模，是当前 effect 流长度不一致
（seed42 1191 旋中 143 旋）的主要来源。

### 24.1 本轮确认的两条通用规则

1. **被销毁的图标，其已经登记的效果仍然生效。** 真机在结算前先把所有
   图标的效果登记好，之后才开始逐个结算；某个图标在本旋被提前销毁，
   不会撤销它登记过的效果。典型例子：灯泡被销毁后，相邻宝石仍然 ×2；
   猫被销毁后仍会吃掉相邻牛奶；猴子被销毁后仍会吃掉相邻椰子半。
   Rust 原来是单趟按格子顺序结算、遇到「已销毁」就跳过整段，导致少算。
   现在对这类「确定性、作用于邻居」的效果单独补了一段登记回放，且不让
   它们消耗随机数，保持 effect 流位置不变。
2. **虚空系符号的「空格奖励」和「自毁判定」看到的盘面不一样。**
   自毁判定在登记时做，看的是本旋开始时的空格；+1 奖励是挂在相邻格子上的
   条件效果，等其它图标销毁、变成空格后才结算。Rust 原来在图标回合内
   一次性算完两件事，于是既少给钱、又会把不该留的虚空符号留下。现在改为
   先预登记所有虚空符号，等销毁集合稳定后再按最终空格数补钱。

由于 `begin_spin(spin_n)` 每旋重新派生 effect 流，末尾多掷的次数不会带到
下一旋。所以第 24.4 节把「流长度不一致」当成头号原因是错的：真机多出来的
是 `check_effects` 末尾的重复登记（`X19` 等），本身不参与当旋的关键判定。
真正没对齐的是 **同一串随机值被用在几次判定上**：真机的带 `rand` 比较在
多轮检查里反复求值，Rust 只求值一次。

### 25.2 保留下来的修复：条件物品也会在销毁后再查一次

真机 `check_effects` 每轮都会重跑 `item.symbol_check()` / `add_conditional_effects()`，
所以「盘面上没有哪种图标超过 N 个」「空格数达到 N」「图标两两不同」这类
条件，在图标被销毁后**反而可能成立**。Rust 原来只看旋初的一个快照。

现在同时用旋初盘面和销毁后的存活盘面判定，任一满足即给付；涉及
`cyan_pepper` / `blue_pepper` / `red_pepper` / `cyan_pepper_essence`。
实测收入一致率 98.48% → 98.52%，有首差异的局 24 → 23，零回归。

- **真机有**，位置 `game/Pop-up.tscn:3125-3128`：一串 `add_item` 奖励全部

### 26.5 为什么剩下 22 局不是「再调几处规则」能收尾的

本轮和第九轮合计 11 组对照实验，只有 2 组净改善，其余 9 组都因为
「概率/条件效果被过度触发」而回归。根因已经收敛清楚：真机的
`check_effects` 是一个**可收敛的重注册循环**（`Main.tscn:4730-4870`），
每轮对 `symbol_positions_to_update` 里的图标重新检查条件效果，带 `rand`
的比较每次重掷；销毁、移除、变形、物品销毁又会触发全盘
`add_conditional_effects()`。Rust 的 `resolve_spin_effects` 是单趟按格子
顺序结算，用 `preregister_symbol_effects` 预先摇号来近似。这两者在
「一个效果有几次判定机会」上无法用局部补丁等价。

要真正到 100%，必须把效果系统改成「登记 → 检查 → 收敛」的多轮结构，
并让随机流消耗顺序与真机逐旋一致。这是核心架构改动，不是继续调规则
能完成的；在此之前不建议用拟合阈值的方式硬凑指标。
